# The Two Calendars: MMM case study

Does a weekly-vs-monthly data mismatch (TV by Monday-to-Sunday media week; digital, email and sales by calendar month) change a marketing-mix-model recommendation to move 15% of TV spend into digital and email? This repo builds the data, the model, the validation checks and the LLM spec reader needed to answer that, on synthetic data with a known true effect per channel.

## Deliverables (open these first)

All three are in [`outputs/`](outputs/).

| File | What it is |
|---|---|
| [`outputs/Solution_Document.docx`](outputs/Solution_Document.docx) | The Solution Document (9 sections: overview, methodology, how I arrived at it, data, evaluation, tech stack, use of LLMs, limitations, submission index) |
| [`outputs/slides.pptx`](outputs/slides.pptx) | 8-slide storytelling deck, white and green, with speaker notes |
| [`outputs/report.html`](outputs/report.html) | Before-and-after view of channel contributions for both TV scenarios (tabs), plus ROI, reallocation impact, validation and LLM claims. Self-contained: just open it in a browser |

## Main result

- The 15% TV to digital/email shift is **not supported by the data**.
- With **steady TV**, the naive calendar manufactures the recommendation (it reports a gain where the truth is a loss); the correct, day-level calendar does not.
- With **heavily pulsed TV**, the calendar error is second-order and both versions say the shift loses sales.
- Bootstrap intervals are optimistic (they covered the true TV share only 25% of the time in the pulsed world).
- Data are synthetic and the true effects are my design, so this validates a method, not the real brand.

## How to run

Install [uv](https://docs.astral.sh/uv/); dependencies install automatically.

```bash
uv run pytest                                              # 33 tests, no network

# scenario A (pulsed TV) and scenario B (steady TV); --llm mock runs fully offline
uv run python run_pipeline.py --sweep 12 --llm mock
uv run python run_pipeline.py --sweep 12 --llm mock --scenario smooth
uv run python run_sensitivity.py

# rebuild the deliverables from the result files
uv run python build_report.py
uv run python build_slides.py
uv run python build_doc.py
```

`run_pipeline.py` writes `outputs/results.json` and `outputs/results_smooth.json`, which the build scripts read. Runs are deterministic for a given seed (main seed 7, sweep seeds 0 to 11).

### Using a live LLM (optional)

Put a key in a git-ignored `.env` file in the project root and choose a backend:

```
GROQ_API_KEY=...        # --llm groq    (openai/gpt-oss-120b)
OPENAI_API_KEY=...      # --llm openai  (gpt-4o-mini)
ANTHROPIC_API_KEY=...   # --llm anthropic (claude-sonnet-5-5)
```

`--llm mock` and `--llm mock-flawed` are offline stand-ins used by the tests; `mock-flawed` injects an invented quote and two misreads to show the verifier catching them.

## How it works, briefly

1. **Generate** daily truth with a known effect per channel (TV 18%, digital 14%, email 6% of sales), published as TV weekly and everything else monthly.
2. **Validate** grain and calendar on every refresh; errors block the model fit.
3. **Read specs** with an LLM; each claim must quote the spec verbatim and pass a data test before it can act.
4. **Aggregate** TV two ways: naive (whole week to one month) and apportioned (each week split over its 7 days).
5. **Fit** the same MMM on both, with a 300-refit bootstrap, and compare channel contributions with intervals.
6. **Decide**: simulate moving 15% of TV into digital and email, and compare with the true effect.
